# Auth PostgreSQL Runtime Role Separation

**Purpose:** document the least-privilege database identities required by the Auth B2 safety-writer contract. This is a production provisioning guide, not evidence that production credentials or grants have been installed.

## Required role classes

| Role                           |                   Login | Use                                                                                         | Required restriction                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------ | ----------------------: | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Auth runtime                   |                     Yes | HTTP requests and ordinary workers (`DATABASE_URL_AUTH`, with `DATABASE_URL` compatibility) | No superuser, database/schema creation, role creation, replication, RLS bypass, schema/table ownership, privileged-role membership, or direct writes to protected status, verification, session, provider, credential, tombstone, SOC journal/resource/receipt, or deletion state. Grant only read access and explicit ordinary profile/contact/outbox writes; column-scope User profile updates. |
| Auth safety writer             |  Yes, restricted secret | `AUTH_SAFETY_DATABASE_URL`, used by the Auth safety transaction service                     | Non-owner and non-superuser, no role membership. Grant only the writes required by SOC and safety-fenced credential/status/session/provider/deletion transactions. Tombstones are append-only; account audit is append-only. This is a trusted internal transaction principal, not an independent authorization authority.                                                                        |
| Migration login                | Yes, migration job only | Schema deployment                                                                           | `NOINHERIT`; no database/schema creation; may explicitly assume the `NOLOGIN` schema owner only for a controlled migration. Never inject this URL into Auth runtime processes.                                                                                                                                                                                                                    |
| Schema owner                   |          No (`NOLOGIN`) | Ownership of Auth schema objects                                                            | Owns schema and relations; not used for application connections.                                                                                                                                                                                                                                                                                                                                  |
| Maintenance / restore operator |   Controlled separately | Role provisioning, schema recovery, backup/PITR and approved repair                         | Keep credentials outside application secrets and runtime workloads. Audit all use and reconcile tombstones, SOC resources, receipts and permanent identity fences before traffic resumes.                                                                                                                                                                                                         |

## Provisioning and configuration procedure

1. Create the roles through the approved DBA/secret-management process. Use unique credentials and do not reuse a schema-owner, migration, maintenance or restore password for Auth runtime.
2. Transfer Auth schema/relation ownership to the non-login schema owner. Revoke `PUBLIC` privileges and grant the Auth runtime only the read/ordinary DML allowlist required by registered operations. Grant protected transactional writes only to the safety writer. Configure default privileges so new tables do not silently become writable by runtime.
3. Validate effective table, column, sequence, schema, database and role-membership privileges using the exact runtime credential. Confirm no runtime ownership, `SET ROLE`, `SET SESSION AUTHORIZATION`, trigger-management, DDL or grant path exists.
4. Configure `DATABASE_URL_AUTH` and `DATABASE_URL` with the runtime credential and `AUTH_SAFETY_DATABASE_URL` with the dedicated safety credential. Keep migration and maintenance URLs out of request/worker environments. Use the deployment secret manager and fail startup when strict/production mode lacks the separate safety URL or expected role configuration.
5. Before enabling any B2 production gate, verify every registered Auth operation with the provisioned credentials, inspect effective grants, and record the environment, schema revision and migration result. This document does not authorize enabling MATCH, DISCLOSURE, deletion, or multi-room features.

Never use a database-owner fallback when a restricted connection fails. Fail startup or fail the affected safety operation closed. PostgreSQL owner/superuser and PITR/restore credentials remain a separate trust boundary and must not be presented as ordinary writer accounts.

## Local acceptance evidence and limits

The guarded disposable acceptance at `chat-backend/logs/anon-chat-b2c8/20261126-40b0b26f74.json` used separate schema-owner, migration, runtime and safety roles. The real Auth process performed registration, email verification, login, refresh, revocation, provider unlink, account-status mutation/retry after restart, deletion and SOC recovery. Direct SQL using the exact runtime role was denied for DDL, trigger disable, role creation/assumption, protected account/session/provider/tombstone/SOC changes, truncate and grant escalation; protected rows were unchanged. No live database was changed and no production role was provisioned by that acceptance.

The safety credential is used by the Auth process for transactions that must atomically write safety evidence and protected source state. Separate PostgreSQL roles prevent an ordinary runtime connection from directly bypassing database enforcement; they do not protect against compromise of the Auth process or exposure of its safety secret. Keep the safety transaction module and secret narrowly controlled and audited. Trusted-owner PITR, restore-time replay and production grant verification remain separate release/operational work.
