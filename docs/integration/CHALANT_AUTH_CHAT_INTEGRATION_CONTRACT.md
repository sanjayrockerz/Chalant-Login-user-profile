The lowercase `users` schema described by the historical crosswalk is not proven to be the active signup identity table. Do not select it merely because Chat previously expected it.

## C. Identity and data ownership

| Data | Owner | Chat behavior |
|---|---|---|
| Canonical UUID | Auth | Read and persist as `authUserId`; never generate or rewrite it. |
| Primary email and verified state | Auth | Consume only through an approved event/API; do not edit locally. |
| Provider identities | Auth | Never copy provider secrets or provider tokens. |
| Passwords, sessions, refresh tokens, OTP/recovery tokens | Auth | Never store or accept in Chat. |
| Account status and global suspension/disablement | Auth | Enforce before Chat authorization; stale projections must fail closed for sensitive actions. |
| Global username/display name/profile image/pronouns | Auth | Fetch or materialize read-only projection with a defined update event. |
| Onboarding and policy consent | Auth | Auth remains the authority; Chat may require a declared eligibility signal. |
| Chat display preferences/notifications | Chat | Chat may create and update. |
| Chat membership, moderation state, Chat roles | Chat | Chat owns, subject to Auth account eligibility. |
| Conversations, messages, reactions | Chat | Chat owns retention and deletion policy; do not cascade-delete without approval. |

Chat may cache Auth profile fields for rendering, but the cache is read-only and must be refreshed by versioned lifecycle events or reconciliation. Chat must not write Auth email, username, account status, verification, onboarding, policy, credential, or provider fields directly.

Required lifecycle behavior:

- New Auth account: create a pending/inactive Chat projection through the outbox.
- Verification/onboarding/activation: update Chat eligibility only through an agreed event or authenticated read.
- Username/profile change: update the Chat read model; never make Chat the writer.
- Suspension/disablement: deny Chat access immediately when authoritative Auth validation says so; asynchronously mark the projection restricted.
- Deletion: follow an approved retention/privacy policy; do not infer hard deletion from a deactivation event.

## D. Roles and authorization

**VERIFIED:** Auth has account statuses `ACTIVE`, `SUSPENDED`, `DISABLED` and canonical JWT validation reloads the session and principal, including account status. **NOT VERIFIED:** the current Chat role schema and scope.

Account eligibility and Chat authorization are separate dimensions:

1. Auth proves the caller is an active, non-revoked canonical principal.
2. Chat proves membership and the required Chat-scoped permission.
3. Conversation/message ownership and moderation rules are evaluated by Chat.

`ACTIVE` does not mean Chat `ADMIN`; `SUSPENDED` does not mean a Chat moderation role; Chat `ADMIN` cannot override an Auth `SUSPENDED` or `DISABLED` account. Any mapping of Auth status to a Chat role is **PROPOSED UNTIL APPROVED** and should not be implemented as an enum cast.

Recommended Chat role scope, **PROPOSED** pending Chat source review: roles are Chat/community scoped, with `USER`, `MODERATOR`, and `ADMIN` permissions stored in Chat-owned membership/role records. Product/security owners must approve whether any role is global, community-scoped, conversation-scoped, or combined.

## F. Provisioning contract

**VERIFIED current Auth implementation:** signup creates a canonical `User` and an outbox row in the same Prisma transaction. The event type is `chat.profile.provision.v1`; `aggregateId` is the Auth UUID; current payload is only `{ "authUserId": "<uuid>" }`. The outbox has a unique `(eventType, aggregateId)` constraint. The worker is registered in `CanonicalAuthModule`, polls every 5 seconds, claims rows with a 60-second lease, sends HTTPS `POST`, and retries failures with exponential backoff capped at one hour. Tests cover accepted delivery and retry after HTTP 503.

**VERIFIED current signing behavior:** the worker sends `x-chat-event-timestamp` and `x-chat-event-signature`, where the signature is hex HMAC-SHA-256 over `${timestamp}.${rawJsonBody}`. It requires HTTPS and configuration `CHAT_PROFILE_PROVISIONING_URL` plus `CHAT_PROFILE_PROVISIONING_HMAC_SECRET`.

This is not yet a complete two-sided protocol: the Chat receiver, timestamp-skew policy, replay cache, key versioning, and receiver idempotency are not present in the inspected Auth source. The following is **PROPOSED IMPLEMENTATION CONTRACT** for Chat approval:

```json
{
  "eventId": "uuid",
  "eventType": "chat.profile.provision.v1",
  "occurredAt": "RFC3339 timestamp",
  "aggregateId": "Auth user UUID",
  "entityVersion": 1,
  "payload": {
    "authUserId": "Auth user UUID",
    "email": "only if Chat rendering requires it",
    "username": "only if approved",
    "displayName": "optional approved projection",
    "isVerified": false,
    "accountStatus": "ACTIVE"
  }
}
```

Minimize PII. Never send passwords, hashes, sessions, refresh tokens, OTP/recovery tokens, provider secrets, contact lists, or contact hashes. The Chat receiver must upsert by `authUserId` and treat `eventId` as an idempotency key. Duplicate events return success without duplicate rows. Older `entityVersion` values are ignored; gaps trigger reconciliation rather than unsafe overwrite.

For the current wire format, HMAC verification is `HMAC-SHA256(secret, timestamp + "." + rawBody)`, constant-time comparison, HTTPS, and a maximum timestamp skew (recommended five minutes). **PROPOSED hardening:** add `x-chat-event-id`, `x-chat-key-id`, and sign method/path/timestamp/event-id/raw-body, or document why the existing format is retained. Key rotation requires overlapping key IDs and receiver support for old/new keys during rollout.

Retryable receiver responses: 408, 429, 5xx, timeout, and network failure. Non-retryable responses: authenticated 400/schema rejection, unless the contract explicitly returns a corrected retryable classification. The receiver must authenticate before processing and must not grant access based solely on a stale projection.

Provisioning is selected as **transactional outbox + authenticated internal HTTP delivery** because that mechanism already exists in Auth; no new broker is justified by current evidence. Initial provisioning can be pending until email verification/onboarding policy is satisfied. A first authenticated Chat request may perform an idempotent upsert only if Chat owner/security approves it and Auth status is freshly validated.

## G. Authentication trust contract

**VERIFIED Auth token facts:** canonical tokens use issuer `r3-canonical-identity`, audience `r3-api`, subject equal to `User.id`, session ID `sid`, type `canonical-access`, and the configured JWT secret. The Auth guard verifies the token and reloads session/principal state from PostgreSQL, including revocation, expiry, and account status.

**PROPOSED Chat integration:** Chat must not receive or distribute the symmetric Auth JWT secret casually. Preferred options are an Auth-issued short-lived token-exchange/introspection mechanism or an API gateway that validates Auth tokens and passes a signed internal principal. A local Chat verifier is acceptable only after Auth publishes a key-distribution and revocation contract; the current symmetric secret is not sufficient for independently deployed trust without explicit security approval.

Chat must require expected issuer, audience, algorithm, token type, subject UUID, expiry, active session, and active Auth account. Expired, revoked, malformed, wrong-audience, wrong-issuer, or status-restricted tokens fail closed. Chat roles are checked only after the Auth principal is accepted. Auth unavailability must deny sensitive operations, not grant access from a stale cache.

The current audience is `r3-api`; whether it explicitly authorizes Chat is **BLOCKED/NOT VERIFIED**. Do not change the audience silently. Approve either a Chat audience/token exchange or an explicit gateway contract.
